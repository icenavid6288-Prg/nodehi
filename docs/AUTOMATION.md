# اتوماسیون با n8n و Make

هدف این بخش: حذف کارهای تکراری دستی از دوش تیم فروشگاه، بدون اینکه یکپارچه‌سازی
تبدیل به نقطه شکست شود.

---

## اصل حاکم: idempotency

هر سناریوی خودکار ممکن است **بیش از یک بار** اجرا شود؛ شبکه قطع می‌شود، سرویس
خارجی تایم‌اوت می‌دهد، و n8n دوباره تلاش می‌کند. اگر سناریو دو بار اجرا شود و
دو بار ایمیل بفرستد یا موجودی را دو بار کم کند، فاجعه است.

راه‌حل: هر رویداد یک `idempotencyKey` یکتا دارد که در جدول `AutomationJob`
قید `unique` خورده است. پیش از اجرای هر کاری، وجود کلید بررسی می‌شود.

```ts
const idempotencyKey = `order-paid:${order.id}`

const existing = await prisma.automationJob.findUnique({ where: { idempotencyKey } })
if (existing?.status === 'SUCCEEDED') return // قبلاً انجام شده

await prisma.automationJob.upsert({
  where: { idempotencyKey },
  update: { attempts: { increment: 1 } },
  create: { type: 'order_processing', payload: { orderId: order.id }, idempotencyKey },
})
```

## قرارداد وب‌هوک

### رویدادهای خروجی (نودهی → n8n)

هنگام رویدادهای کلیدی، نودهی یک درخواست POST به آدرس تنظیم‌شده (کلید
`automation.webhookUrl` در پنل، یا متغیر `AUTOMATION_WEBHOOK_URL`) می‌فرستد:

```http
POST {AUTOMATION_WEBHOOK_URL}
Content-Type: application/json
x-nodehi-signature: <hmac-sha256 به شکل hex از بدنه خام، بدون پیشوند sha256=>
```

قالب بدنه: `{ id, event, occurredAt, data }`. `id` شناسه یکتای رویداد است و در
«ارسال دوباره» **تغییر نمی‌کند** — با همین فیلد در سمت n8n از پردازش تکراری
جلوگیری کنید.

```json
{
  "id": "evt_mfk2p1_a9x3k",
  "event": "order.created",
  "occurredAt": "2026-09-27T14:43:25.937Z",
  "data": {
    "orderId": "ND-819298",
    "paymentMethod": "online",
    "total": 80100000,
    "discount": 8900000,
    "shipping": 0,
    "coupon": "NODEHI10",
    "customerPhone": "09120000000",
    "itemCount": 1,
    "items": [{ "slug": "samsung-side-by-side-rs68-28ft", "quantity": 1 }]
  }
}
```

`data` هر رویداد فیلدهای خودش را دارد (مقدارها همان چیزی است که در
`src/app/api/*/route.ts` دیده می‌شود؛ برای جزئیات تغییر نیافته به همان فایل‌ها نگاه
کنید تا سند و کد از هم جدا نشوند):

| رویداد | فیلدهای `data` |
| --- | --- |
| `order.created` | `orderId`، `paymentMethod`، `total`، `discount`، `shipping`، `coupon`، `customerPhone`، `itemCount`، `items` |
| `order.status_changed` | `orderId`، `from`، `to`، `customerPhone`، `trackingCode` |
| `contact.submitted` | `ticketId`، `name`، `phone`، `email`، `subject`، `messageLength`، `userId` |
| `stock_alert.created` | `subscriptionId`، `slug`، `productName`، `phone`، `email` |
| `review.submitted` | `reviewId`، `productSlug`، `rating`، `author` |

> **این جدول با کد یکی است.** نام رویدادها و کلیدهای روشن/خاموش در
> `EVENT_TOGGLE_KEYS` (`src/lib/server/automation.ts`) تعریف شده‌اند؛ اگر رویدادی
> اضافه کردید، همان‌جا و همین سند را به‌روز کنید.

### امضای درخواست

```ts
import { createHmac, timingSafeEqual } from 'node:crypto'

export function signPayload(payload: unknown): string {
  const secret = process.env.AUTOMATION_WEBHOOK_SECRET!
  const body = JSON.stringify(payload)
  return createHmac('sha256', secret).update(body).digest('hex')
}

export function verifySignature(rawBody: string, signature: string): boolean {
  const secret = process.env.AUTOMATION_WEBHOOK_SECRET
  if (!secret) return false

  const expected = createHmac('sha256', secret).update(rawBody).digest('hex')
  const received = signature.replace(/^sha256=/, '')

  // مقایسه زمان‌ثابت — جلوگیری از حمله کانال جانبی
  const a = Buffer.from(expected, 'hex')
  const b = Buffer.from(received, 'hex')
  return a.length === b.length && timingSafeEqual(a, b)
}
```

نکات امنیتی وب‌هوک ورودی:

1. **امضا را بررسی کنید.** وب‌هوک بدون امضا یعنی هر کسی می‌تواند با یک درخواست
   ساختگی موجودی را تغییر دهد یا سفارش جعلی ثبت کند.
2. **زمان را بررسی کنید.** اگر `X-Nodehi-Timestamp` بیش از ۵ دقیقه قدیمی باشد،
   درخواست را رد کنید (جلوگیری از حمله بازپخش).
3. **تکرار را تشخیص دهید.** با `deliveryId` از پردازش دوباره جلوگیری کنید.
4. **محدودیت حجم بدنه** بگذارید تا کسی با بدنه چند مگابایتی سرور را از پا نیندازد.

## سناریوهای اتوماسیون

### ۱. پردازش سفارش (محرک: `order.paid`)

این مهم‌ترین سناریوست؛ کل تجربه پس از خرید به آن وابسته است.

```
[Webhook: order.paid]
   ↓
[بررسی idempotencyKey]  → اگر اجرا شده، پایان
   ↓
[بررسی موجودی هر قلم در انبار]
   ├─ موجود نیست → [اطلاع به اپراتور + پیشنهاد جایگزین] → پایان
   └─ موجود است ↓
[رزرو موجودی]  (Inventory.reserved += quantity)
   ↓
[تولید برچسب ارسال]  → API تیپاکس/پست بر اساس روش انتخابی
   ↓
[ذخیره trackingCode در سفارش]
   ↓
[ایمیل فاکتور + پیامک تأیید سفارش]
   ↓
[اطلاع به تیم فروش در تلگرام/اسلک]
   ↓
[ثبت در AuditLog]
```

**نکته مهم:** رزرو انبار (افزایش `reserved`) با کاهش `quantity` فرق دارد.
اگر بلافاصله موجودی را کم کنید و بعد سفارش لغو شود، باید برگردانید. با مفهوم
رزرو، موجودی واقعی فقط هنگام تحویل کم می‌شود:

```
موجودی قابل فروش = Inventory.quantity − Inventory.reserved
```

این فرمول را در همه جای سایت — از نمایش «تنها ۳ عدد باقی مانده» تا بررسی نهایی
در تسویه حساب — استفاده کنید.

### ۲. همگام‌سازی موجودی (زمان‌بند: هر ۱۵ دقیقه)

```
[Cron: هر ۱۵ دقیقه]
   ↓
[خواندن تغییرات انبار از آخرین اجرا]
   ↓
[برای هر کالای تغییر‌یافته:]
   ├─ به‌روزرسانی سایت (منبع حقیقت)
   ├─ به‌روزرسانی دیجی‌کالا از طریق API فروشندگان
   ├─ به‌روزرسانی فید ترب
   └─ ثبت نتیجه در ChannelListing.lastSyncedAt
   ↓
[در صورت خطای هر کانال → ثبت syncError و تلاش مجدد در اجرای بعدی]
```

مهم: **کانال‌ها را موازی به‌روزرسانی نکنید** بدون مدیریت خطا. اگر دیجی‌کالا
خطا بدهد و سایت موفق شود، باید بدانید کدام کانال عقب مانده است. `syncError`
دقیقاً برای همین است.

### ۳. هشدار موجودی بحرانی و سفارش خرید خودکار (محرک: `stock.low`)

```
[زمان‌بند روزانه]
   ↓
[یافتن کالاهایی که موجودی قابل فروش < آستانه]
   ↓
[محاسبه سرعت فروش ۳۰ روز گذشته]
   ↓
[محاسبه نقطه سفارش = سرعت فروش × زمان تأمین + ذخیره اطمینان]
   ↓
[ساخت پیش‌نویس PurchaseOrder برای تأمین‌کننده]
   ↓
[اطلاع به مدیر خرید با اعداد پیشنهادی]  → تأیید انسانی
```

**سفارش خرید را کاملاً خودکار نفرستید.** سرعت فروش می‌تواند به‌دلیل کمپین یا
فصل کاملاً تغییر کند. پیش‌نویس همراه اعداد به مدیر بدهید و ارسال نهایی را به
تأیید او بسپارید.

### ۴. چت‌بات پشتیبانی

تلفیق چت‌بات با همان داده سایت:

- **پرسش‌های تکراری** ← پاسخ از `src/lib/data/content.ts` (منبع واحد با صفحه سوالات متداول)
- **پیگیری سفارش** ← پرسش شماره سفارش + تأیید هویت با شماره همراه ثبت‌شده
- **مشاوره خرید** ← همان منطق فیلتر پیشرفته (متراژ، تعداد نفرات، بودجه → BTU و ظرفیت)
- **انتقال به اپراتور** ← اگر دو پاسخ ناموفق یا درخواست کاربر

### ۵. بازاریابی خودکار

| سناریو | زمان‌بندی | محتوا |
| --- | --- | --- |
| پیام تشکر پس از خرید | ۱ روز بعد از تحویل | درخواست ثبت نظر + امتیاز باشگاه |
| درخواست نظر | ۳ روز بعد از تحویل | پیوند مستقیم به فرم نظر همان کالا |
| بازیابی سبد رهاشده | ۴ ساعت بعد | پیوند بازگشت به سبد + کد تخفیف در صورت نیاز |
| پیشنهاد مکمل | ۷ روز بعد از خرید | لوازم مرتبط (مثلاً خرید لباسشویی → پودر و محافظ برق) |
| یادآوری سرویس | ۶ ماه بعد | سرویس دوره‌ای و بررسی فیلتر |
| تولد | روز تولد | کد تخفیف اختصاصی |

**قواعد جلوگیری از آزار کاربر:**

- حداکثر **یک پیام تبلیغاتی در هفت روز** برای هر کاربر.
- خارج از ساعت ۹ صبح تا ۹ شب پیام تبلیغاتی نفرستید.
- اگر کاربر سه پیام پیاپی را باز نکرد، ارسال را متوقف کنید.
- پس از لغو اشتراک، حداکثر تا ۲۴ ساعت ارسال را قطع کنید (نه در اجرای بعدی cron).

### ۶. ادغام ERP/CRM

دو حالت دارد:

**الف) ERP داخلی:** از طریق API دوطرفه. کالا و موجودی از ERP به سایت می‌آید،
سفارش‌ها از سایت به ERP می‌رود. منبع حقیقت کالا: ERP. منبع حقیقت سفارش آنلاین: سایت.

**ب) SaaS خارجی:** با همگام‌سازی زمان‌بند و کلید تفکیک بر اساس `updatedAt`.

در هر دو حالت، **فیلدهای همگام‌سازی را مشخص کنید.** اگر ERP نام و توضیح کالا را
بازنویسی کند، متنی که کارشناس محتوا زحمت کشیده از بین می‌رود. فیلدهای مدیریت‌شده
توسط هر طرف را در جدول `ChannelListing` یا یک جدول تنظیمات نگه دارید.

### ۷. گزارش‌گیری خودکار (زمان‌بند: روزانه ۸ صبح)

گزارش روزانه برای مدیران شامل:

```
فروش دیروز:        مبلغ کل / تعداد سفارش / میانگین سبد
مقایسه:            نسبت به روز مشابه هفته قبل و ماه قبل
کانال فروش:        سهم سایت / دیجی‌کالا / ترب
محصولات برتر:      ۵ کالای پرفروش با تعداد
سبدهای رهاشده:     تعداد و مبلغ بالقوه
موجودی بحرانی:     کالاهای زیر آستانه با سرعت فروش
مرجوعی و کنسلی:    نرخ و دلایل
```

گزارش هفتگی تحلیلی‌تر: روند فروش، عملکرد دسته‌بندی‌ها، وفاداری مشتریان تکراری.

## پیاده‌سازی ارسال رویداد

ارسال **همین حالا پیاده شده است** و نمونه کد بیرونی لازم نیست:

| فایل | نقش |
| --- | --- |
| `src/lib/server/automation.ts` | `dispatchAutomationEvent`، `retryAutomationEvent`، نگاشت رویداد به کلید روشن/خاموش |
| `src/lib/server/webhook.ts` | فقط امضا: `signPayload` / `verifySignature` (هم ورودی، هم خروجی) |
| `src/lib/server/settings.ts` | ترتیب خواندن مقدار: دیتابیس (پنل) → متغیر محیطی → پیش‌فرض |

قواعدی که در پیاده‌سازی رعایت شده و باید حفظ شوند:

- **بدون کلید امضا هیچ ارسالی انجام نمی‌شود.** رویداد با وضعیت `skipped` ثبت می‌شود.
  وبهوک بدون امضا یعنی هر کسی می‌تواند رویداد جعلی بفرستد.
- **مهلت پاسخ** از `automation.timeoutMs` (پیش‌فرض ۴۰۰۰ میلی‌ثانیه) می‌آید تا
  کندی n8n، درخواست کاربر را معطل نکند.
- **هر تلاش ثبت می‌شود** (`AutomationEvent`): وضعیت `sent` / `failed` / `skipped`،
  کد پاسخ HTTP، شمار تلاش و متن خطا.
- **ارسال دوباره از پنل** (`/admin/automation`) بدنه ذخیره‌شده را عیناً می‌فرستد، پس
  شناسه رویداد و امضا ثابت می‌ماند.
- **شکست هرگز مسیر اصلی را متوقف نمی‌کند** — ثبت سفارش حتی با n8n خراب انجام می‌شود.

پیاده‌سازی مرجع (بخش اصلی همان فایل بالا):

```ts
const result = await deliver(body, url, secret, timeoutMs, 1)

async function deliver(body, url, secret, timeoutMs, attempts) {
  try {
    const response = await fetch(url, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        [SIGNATURE_HEADER]: signPayload(body, secret),
      },
      body,
      // تایم‌اوت — n8n نباید درخواست را معلق نگه دارد
      signal: AbortSignal.timeout(timeoutMs),
    })

    if (response.ok) return { status: 'sent', responseStatus: response.status }
    return { status: 'failed', responseStatus: response.status, error: `پاسخ وبهوک: ${response.status}` }
  } catch (error) {
    // شکست در catch هم ثبت می‌شود؛ چیزی بی‌ردپا نمی‌ماند
    return { status: 'failed', error: `تلاش ${attempts}: ${error.message}` }
  }
}
```

قاعده طلایی: **شکست اتوماسیون هرگز نباید سفارش یا پرداخت را از کار بیندازد.**
اتوماسیون لایه رفاه است، نه لایه حیاتی. همیشه در حالت خطا، لاگ و ذخیره کن و
اجازه بده جریان اصلی ادامه پیدا کند.

## نکات عملیاتی n8n

| موضوع | توصیه |
| --- | --- |
| میزبانی | n8n را روی سرور **جدا** از فروشگاه اجرا کنید تا مصرف منابع آن روی سایت اثر نگذارد |
| دسترسی | n8n باید از طریق شبکه خصوصی یا IP سفیدلیست‌شده به API فروشگاه وصل شود |
| اعتبارنامه‌ها | در «Credentials» n8n ذخیره شود، نه داخل گره‌ها |
| خطاها | برای هر سناریو یک «Error Workflow» تعریف کنید که شکست را به تلگرام یا ایمیل بفرستد |
| نسخه‌بندی | گردش‌کارها را export و در Git نگه دارید |
| تست | برای هر سناریو یک محیط آزمایشی با داده واقعی اما محیط sandbox درگاه پرداخت داشته باشید |
| اجرای دوباره | «Retry On Fail» را فعال کنید، اما همیشه با فیلد `id` رویداد به‌عنوان کلید idempotency |
| نظارت | پنل `/admin/automation` را روزانه نگاه کنید: رویدادهای `failed` را از همان‌جا دوباره بفرستید |

بدون «Error Workflow» هرگز نمی‌فهمید اتوماسیون از کار افتاده است تا زمانی که
مشتری زنگ بزند و بگوید سفارشش را نگرفته — و آن موقع دیگر دیر است.
