# راهنمای اتصال به سرویس‌های خارجی

هر بخش شامل: متغیرهای محیطی لازم، محل قرارگیری کد، نمونه پیاده‌سازی و نکات
مهم عملیاتی است.

> **قاعده کلی:** هر سرویس خارجی باید پشت یک ماژول در `src/lib/server/` پنهان
> شود (اگر فقط در مرورگر اجرا می‌شود، `src/lib/services/`). کامپوننت‌ها و
> API Routes هرگز مستقیم با SDK سرویس حرف نزنند. با این کار تغییر
> ارائه‌دهنده (مثلاً از کاوه‌نگار به فراز اس‌ام‌اس) فقط یک فایل را تغییر می‌دهد.

## ۱. درگاه پرداخت

### زرین‌پال (تنها درگاه فعال)

پیاده‌سازی واقعی است، نه نمونه. چرخه کامل کار می‌کند: درخواست پرداخت،
هدایت به درگاه، و تأیید بازگشت.

| فایل | مسئولیت |
| --- | --- |
| `src/lib/server/payments/zarinpal.ts` | پروتکل درگاه: endpoint، تفسیر پاسخ، کدهای خطا، پیکربندی |
| `src/lib/server/payments/flow.ts` | سیاست نودهی: کدام سفارش، چه زمانی `paid` شود، چه رویدادی اعلام شود |
| `src/app/api/payments/zarinpal/callback/route.ts` | بازگشت مرورگر کاربر از درگاه |
| `src/app/checkout/result/page.tsx` | صفحه نتیجه پرداخت |

```env
# مقدارهای جایگزین؛ اولویت با پنل /admin/payments است
ZARINPAL_MERCHANT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
ZARINPAL_CALLBACK_URL="https://nodehi.ir/api/payments/zarinpal/callback"
# فقط برای آزمون محلی یا پروکسی
ZARINPAL_API_BASE=""
ZARINPAL_STARTPAY_BASE=""
```

**جریان کار:**

```
۱. کاربر «پرداخت آنلاین» را انتخاب می‌کند
۲. POST /api/checkout
   ├─ اعتبارسنجی سبد و قیمت‌گذاری روی سرور (هرگز از مرورگر)
   ├─ بررسی فعال بودن درگاه از پنل مدیریت → اگر خاموش باشد، ۴۰۰
   ├─ ساخت سفارش با وضعیت pending
   └─ startOnlinePayment → دریافت authority و ذخیره روی Order.paymentAuthority
۳. هدایت کاربر به {startPay}/{authority}
۴. بازگشت کاربر به /api/payments/zarinpal/callback?Authority=...&Status=OK
۵. verify از API زرین‌پال (همیشه، حتی وقتی Status=NOK است)
۶. موفق (کد ۱۰۰ یا ۱۰۱)
   └─ Order.status = paid، ثبت paymentRefId و paidAt و ۴ رقم آخر کارت
      + لاگ حسابرسی order.paid + رویداد اتوماسیون order.paid
   ناموفق
   └─ سفارش pending می‌ماند (قابل پرداخت دوباره)، رویداد payment.failed
۷. ریدایرکت به /checkout/result?state=... برای نمایش نتیجه به کاربر
```

**نکات حیاتی:**

- **پنل مدیریت منبع حقیقت است.** فعال/غیرفعال بودن، حالت آزمایشی و شناسه
  پذیرنده از ردیف درگاه در دیتابیس خوانده می‌شوند (`/admin/payments`)، و فقط
  اگر آنجا مقداری ثبت نشده باشد متغیر محیطی جایگزین می‌شود. اگر مدیر درگاه
  آنلاین را خاموش کند، هیچ پرداخت تازه‌ای — حتی با درخواست دستی به API —
  آغاز نمی‌شود.
- **خاموش‌کردن درگاه، تأیید تراکنش باز را نمی‌بندد.** پیکربندی دو پرچم جدا
  دارد: `ready` برای *شروع* پرداخت و `verifyReady` برای *تأیید* آن. اگر کسی
  درگاه را وسط تراکنش خاموش کند، پول مشتری باید همچنان قابل تأیید بماند.
- **واحد پول: ریال در هر دو متد.** قیمت‌های کاتالوگ نودهی تومان است؛ تنها
  نقطه تبدیل تابع `toRial` است و همان مبلغ ریالی هم به `request` و هم به
  `verify` می‌رود. پارامتر `currency` عمداً فرستاده نمی‌شود؛ اگر یکی از دو متد
  تومان و دیگری ریال ببیند، درگاه تراکنش را با خطای ‎-50 رد می‌کند.
- **سقف تراکنش ۱۰۰ میلیون تومان** است و پیش از تماس با شبکه بررسی می‌شود،
  تا خطای ‎-41 در میانه خرید رخ ندهد.
- **کد `101` خطا نیست.** یعنی تراکنش قبلاً تأیید شده است. اگر آن را خطا بگیریم،
  مشتری با رفرش صفحه پولش را داده ولی سفارشش `pending` می‌ماند.
- **هرگز به `Status` بازگشتی از مرورگر اعتماد نکنید.** تصمیم نهایی همیشه
  خروجی متد `verify` است؛ آن مسیر امضا ندارد و هر کسی می‌تواند آن آدرس را باز کند.
- **تأیید idempotent است.** `paymentAuthority` یکتاست، سفارشِ `paid` دوباره
  وریفای نمی‌شود و به‌روزرسانی وضعیت با شرط `status = 'pending'` انجام
  می‌گیرد تا دو بازگشت هم‌زمان فقط یک بار اثر بگذارند.
- **خطای ارتباطی با خطای قطعی فرق دارد.** در خطای شبکه `authority` پاک
  نمی‌شود (ممکن است پول رسیده باشد و فقط پاسخ به ما نرسیده باشد) و سفارش
  `unverifiable` علامت می‌خورد تا دستی بررسی شود.
- `card_pan` فقط به شکل ۴ رقم آخر ذخیره می‌شود (`****1234`).
- **آدرس بازگشت باید با دامنه ثبت‌شده در زرین‌پال یکی باشد**، وگرنه درگاه
  تراکنش را با خطای ‎-14 رد می‌کند. این شایع‌ترین خطای محیط تولید است.

**آزمون بدون پول واقعی:** با تنظیم `ZARINPAL_API_BASE` و
`ZARINPAL_STARTPAY_BASE` می‌توان کل چرخه را به یک درگاه شبیه‌سازی‌شده محلی
هدایت کرد. منطق تفسیر پاسخ و پیکربندی هم واحد‌آزمون دارد
(`src/lib/server/payments/zarinpal.test.ts`).

### آیدی‌پی

```env
IDPAY_API_KEY="..."
```

ساختار مشابه است، با این تفاوت که آیدی‌پی هدر `X-API-KEY` می‌خواهد و مبلغ را
به **ریال** می‌گیرد. پاسخ آن `id` تراکنش را برمی‌گرداند که باید برای verify
ذخیره شود.

### پرداخت درب منزل

نیازی به سرویس خارجی ندارد. جریان کار:

1. `Order.paymentMethod = CASH_ON_DELIVERY`، `status = PROCESSING`
2. رزرو انبار انجام می‌شود اما پرداخت ثبت نمی‌شود
3. هنگام تحویل، مامور ارسال مبلغ را دریافت و در پنل ثبت می‌کند
4. سفارش به `DELIVERED` منتقل می‌شود

برای سفارش‌های بالای ۱۰۰ میلیون تومان، پیش‌پرداخت الزامی کنید تا ریسک
نپذیرفتن کالا توسط مشتری کاهش یابد.

### خرید اقساطی

از سرویس‌های اعتبارسنجی (دیجی‌پی و مشابه) استفاده می‌شود. جریان:

1. انتخاب «خرید اقساطی» → انتقال به سرویس اعتبارسنجی
2. کاربر مدارک را بارگذاری می‌کند (کاربرگ توسط خود سرویس مدیریت می‌شود)
3. سرویس نتیجه را به وب‌هوک نودهی اعلام می‌کند
4. تأیید → `Payment.method = INSTALLMENT`، `status = SUCCESS`
5. رد → سفارش `CANCELLED` و به کاربر اطلاع داده می‌شود

**مهم:** مسئولیت پرداخت اقساط بر عهده سرویس اعتبارسنجی است، نه نودهی. شرط
بازگشت کالا در خرید اقساطی باید با آن سرویس هماهنگ شود.

## ۲. پیامک — کاوه‌نگار

> **پیاده‌سازی واقعی:** ماژول فعال `src/lib/server/sms.ts` است (نه مسیر نمونه زیر) و
> مقدارهایش از **تنظیمات پنل** خوانده می‌شوند: `/admin/sms` برای فعال‌سازی، کلید
> API، شماره فرستنده و قالب‌ها. هر ارسال، موفق یا ناموفق، در جدول `SmsMessage`
> ثبت می‌شود و فرم «پیامک آزمایشی» همان صفحه اتصال را می‌سنجد. متغیرهای زیر
> فقط مقدارهای جایگزین هستند و اگر تنظیمی در پنل ثبت شود، **پنل اولویت دارد**.

```env
SMS_PROVIDER="kavenegar"
KAVENEGAR_API_KEY="..."
KAVENEGAR_SENDER="10008663"
KAVENEGAR_OTP_TEMPLATE=""
```

```ts
// src/lib/services/sms/kavenegar.ts
export async function sendSms(params: {
  receptor: string
  message?: string
  template?: string
  token?: string
}) {
  const apiKey = process.env.KAVENEGAR_API_KEY
  if (!apiKey) return { skipped: true as const }

  // برای پیامک خدماتی (کد ورود، وضعیت سفارش) از قالب استفاده کنید،
  // چون ارسال سریع‌تر است و در سامانه ثبت می‌شود.
  const base = `https://api.kavenegar.com/v1/${apiKey}`
  const url = params.template
    ? `${base}/verify/lookup.json?receptor=${params.receptor}&template=${params.template}&token=${params.token}`
    : `${base}/sms/send.json?receptor=${params.receptor}&sender=${process.env.KAVENEGAR_SENDER}&message=${encodeURIComponent(params.message ?? '')}`

  const response = await fetch(url, { method: 'GET' })
  return response.json()
}
```

**پیامک‌های ضروری فروشگاه:**

| رویداد | قالب | توکن |
| --- | --- | --- |
| کد ورود | `nodehi-otp` | کد ۶ رقمی |
| ثبت سفارش | `nodehi-order-placed` | شماره سفارش |
| ارسال مرسوله | `nodehi-order-shipped` | شماره سفارش + کد رهگیری |
| تحویل سفارش | `nodehi-order-delivered` | شماره سفارش |
| موجود شدن کالا | `nodehi-back-in-stock` | نام کالا |
| بازیابی سبد رهاشده | `nodehi-abandoned-cart` | لینک بازگشت |

**نکات عملیاتی:**

- پیامک تبلیغاتی فقط با `User.marketingOptIn = true` ارسال شود. ارسال بدون
  رضایت، هم خلاف قانون است و هم باعث شکایت کاربران می‌شود.
- سقف ارسال روزانه را کنترل کنید تا هزینه از دستتان خارج نشود.
- در جدول `Notification` هر ارسال ثبت شود تا از ارسال تکراری جلوگیری شود.
- خارج از ساعات ۹ صبح تا ۹ شب پیامک تبلیغاتی نفرستید.

## ۶. مارکت‌پلیس

> **وضعیت پیاده‌سازی:** جای اتصال و اعتبارنامه‌ها آماده است، پنل
> `/admin/integrations` همه را پیش‌فرض **غیرفعال** نگه می‌دارد. تنها بخش واقعی
> فعلاً فید ترب است؛ همگام‌سازی دیجی‌کالا و پرداخت اسنپ‌پی هنوز کد سمت سرویس
> ندارند و فعال‌کردنشان در پنل اثری ندارد.

```env
SNAPPAY_MERCHANT_ID=""
SNAPPAY_API_KEY=""
DIGIKALA_SELLER_ID=""
DIGIKALA_VENDOR_API_KEY=""
TOROB_API_KEY=""
```

**اسنپ‌پی (پرداخت اعتباری/BNPL):** برای تقسیط سبد خرید. اعتبارنامه از پنل یا
متغیر محیطی خوانده می‌شود. تا پیاده‌سازی اتصال واقعی، گزینه‌ای در تسویه حساب
نمایش داده نمی‌شود — کلید `integration.snappPay.enabled` هیچ مسیری را باز
نمی‌کند. الگوی پیاده‌سازی آینده همان الگوی زرین‌پال است: ماژول پروتکل در
`src/lib/server/payments/` + یک روش پرداخت جدید در پنل درگاه‌ها.

**دیجی‌کالا (فروشنده):** از API فروشندگان برای ساخت خودکار محصول، همگام‌سازی
قیمت و موجودی و دریافت سفارش استفاده می‌شود. جدول `ChannelListing` وضعیت
همگام‌سازی هر کالا در هر کانال را نگه می‌دارد.

**ترب:** ترب واسط مقایسه قیمت است. پیاده‌سازی فعلی یک **فید JSON** است:
با فعال‌کردن «یکپارچه‌سازی‌ها → ترب» در پنل، مسیر `GET /api/feeds/torob`
فهرست کالاهای فعال را با `pid` (نامک)، `title`، `price`، `old_price`،
`availability`، `url` مطلق و `image_url` می‌دهد. تا وقتی خاموش است همین مسیر
۴۰۴ می‌دهد. اگر ترب فرمت XML خواست، همین داده از یک روت دیگر سریالایز می‌شود.
فید شامل: نام،
قیمت، موجودی، لینک، تصویر و برند.

**قاعده مهم همگام‌سازی:** منبع حقیقت موجودی، انبار خود فروشگاه است. وقتی موجودی
در انبار تغییر می‌کند، ابتدا در دیتابیس اصلی ثبت شود، سپس از طریق صف به کانال‌های
خارجی منتشر شود. اگر به‌صورت موازی به هر کانال بنویسید، در اولین خطای شبکه
داده‌ها ناهمگام می‌شوند و کالای ناموجود در یک کانال باقی می‌ماند.

```ts
// ۱. ابتدا تغییر در دیتابیس اصلی ثبت می‌شود
await prisma.$transaction([
  prisma.product.update({
    where: { id: productId },
    data: { stock: { decrement: quantity } },
  }),
  prisma.stockMovement.create({
    data: {
      productId,
      warehouseId,
      delta: -quantity,
      reason: 'SALE',
      reference: orderNumber,
    },
  }),
])

// ۲. سپس از یک صف واحد به کانال‌های خارجی منتشر می‌شود
await enqueue('stock_sync', { productId, quantity })
```

## ۷. چت‌بات و پشتیبانی آنلاین

```env
CHATBOT_PROVIDER="custom"   # custom | ramona
CHATBOT_API_KEY="..."
```

چت‌بات نودهی باید سه کار را خوب انجام دهد:

1. **پاسخ به پرسش‌های تکراری** — با استفاده از همان محتوای `src/lib/data/content.ts`
   (سوالات متداول). پاسخ‌ها باید از یک منبع واحد بیایند تا بین چت‌بات و سایت
   تناقض ایجاد نشود.
2. **پیگیری سفارش** — با پرسیدن شماره سفارش و کد ملی/همراه، وضعیت را از دیتابیس
   می‌خواند. **احراز هویت لازم است**؛ هرگز وضعیت سفارش را فقط با شماره سفارش
   نشان ندهید، چون قابل حدس زدن است.
3. **مشاوره خرید** — با پرسیدن سوالات هدایت‌کننده (متراژ، تعداد اعضای خانواده،
   بودجه) محصول مناسب را پیشنهاد می‌دهد. همین منطق در ابزار مقایسه سایت هم
   استفاده می‌شود.

انتقال به اپراتور انسانی: اگر چت‌بات دو بار پیاپی پاسخ نامناسب داد یا کاربر
درخواست کرد، مکالمه باید فوراً به اپراتور منتقل شود و کل تاریخچه گفتگو همراه
باشد.

## خلاصه متغیرها

| سرویس | متغیرهای الزامی | اگر تنظیم نشود |
| --- | --- | --- |
| سایت | `NEXT_PUBLIC_SITE_URL` | آدرس canonical و سایت‌مپ اشتباه می‌شود |
| دیتابیس | `DATABASE_URL` | فقط داده نمایشی، بدون ذخیره‌سازی |
| کش | `REDIS_URL` | کش غیرفعال، برنامه کار می‌کند |
| احراز هویت | `AUTH_OTP_DEV_MODE`, `AUTH_OTP_TTL_SECONDS` | بدون کد پیامکی، با `AUTH_OTP_DEV_MODE=1` کد روی صفحه نشان داده می‌شود |
| پیامک | `KAVENEGAR_API_KEY` (یا تنظیم پنل `/admin/sms`) | کد ورود در کنسول سرور چاپ می‌شود (حالت توسعه) |
| رمزنگاری تنظیمات | `SETTINGS_ENCRYPTION_KEY` | مقدارهای حساس پنل متن ساده ذخیره می‌شوند و پنل هشدار می‌دهد |
| پرداخت | `ZARINPAL_MERCHANT_ID` (یا پنل `/admin/payments`) | درگاه آنلاین خاموش می‌ماند و فقط پرداخت درب منزل و اقساطی فعال است |
| آدرس بازگشت پرداخت | `ZARINPAL_CALLBACK_URL` | از `NEXT_PUBLIC_SITE_URL` ساخته می‌شود؛ در تولید باید با دامنه ثبت‌شدهٔ درگاه یکی باشد وگرنه خطای ‎-14 |
| ایمیل | `SMTP_*` | ایمیل‌ها در لاگ ثبت می‌شوند |
| تصاویر | `S3_*` | تصاویر محلی استفاده می‌شوند |
| اتوماسیون | `AUTOMATION_WEBHOOK_URL`, `AUTOMATION_WEBHOOK_SECRET` (یا پنل `/admin/automation`) | رویدادها با وضعیت `skipped` در جدول رویدادها ثبت می‌شوند، همراه دلیل فارسی |
| وبهوک ورودی | `NODEHI_WEBHOOK_SECRET` | `POST /api/webhooks/order-paid` با ۵۰۳ بسته می‌ماند |

فلسفه طراحی: **نبود هر سرویس اختیاری نباید برنامه را از کار بیندازد.** سرویس‌های
خارجی همیشه از کار می‌افتند؛ کد باید این وضعیت را تحمل کند و به‌جای خطای
۵۰۰، مقدار نمایشی برگرداند.

**اولویت تنظیمات پنل:** هر کلیدی که از `/admin/settings`, `/admin/sms` یا
`/admin/automation` ذخیره شود، بر متغیر محیطی هم‌نامش مقدم است (ترتیب خواندن:
دیتابیس → متغیر محیطی → پیش‌فرض کد). پس محیط تولید می‌تواند فقط رازها را در متغیر
محیطی نگه دارد و بقیه را به تیم عملیات بسپارد. مقدارهای نوع `secret` هم با
`SETTINGS_ENCRYPTION_KEY` رمزنگاری (AES-256-GCM) و از API فقط به شکل `hasValue`
برگردانده می‌شوند.
