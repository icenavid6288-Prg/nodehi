# بررسی فنی مهاجرت: Next.js → React (Vite) + Laravel

این سند نتیجهٔ بررسی کد موجود در مخزن است، نه برنامهٔ مهاجرت. هدفش پاسخ به یک
پرسش است: **در وضعیت فعلی، مهاجرت کجا ایستاده، چه چیزهایی شکسته است و برای
رسیدن به یک فروشگاه قابل انتشار چه باید کرد؟**

- دامنهٔ بررسی: `src/` (نسخهٔ Next)، `frontend/` (React)، `backend/` (Laravel)،
  `scripts/`، `docs/` و `prisma/`.
- روش: خواندن کد، مقایسهٔ endpoint‌ها و مسیرها، اجرای typecheck و build فرانت‌اند.
- محدودیت: در این محیط PHP و Composer نصب نیست؛ بک‌اند اجرا نشد و تست‌های
  Laravel اجرا نشدند. یافته‌های بک‌اند از روی کد و migration‌ها است (به همین دلیل
  در بخش ۹ تفکیک شده‌اند).

> **توجه:** بخش‌های ۳ و ۴ وضعیت **پیش از اصلاح** را توصیف می‌کنند. موارد P0 و
> چند باگ کلاینت در دور بعد رفع شدند و در بخش ۱۰ فهرست شده‌اند.

## ۱. خلاصهٔ مدیریتی

اسکلت مهاجرت سالم است: API لاراول تمیز نوشته شده، قیمت‌گذاری سمت سرور است،
migration و مدل‌ها کامل‌اند و فرانت‌اند React بدون خطای نوع و با بیلد موفق
کامپایل می‌شود. اما پروژه در سه لایه با نسخهٔ Next فاصله دارد:

| لایه | وضعیت واقعی |
| --- | --- |
| صفحات عمومی فروشگاه | ~۷۰٪ منتقل شده؛ چند قابلیت حذف شده (مقایسه، علاقه‌مندی، زیرصفحه‌های حساب، نصب) |
| قابلیت‌های کسب‌وکار (ادمین، پرداخت، اتوماسیون) | ~۰٪ در لاراول؛ فقط جدول‌ها ساخته شده‌اند |
| سئوی فنی | ~۱۰٪؛ SPA بدون متادیتای صفحه، بدون sitemap و با ریدایرکت صفحات دسته/برند |
| کیفیت و امنیت | چند رگرسیون جدی نسبت به نسخهٔ Next که در بخش ۳ آمده است |

**نتیجه:** الان نمی‌توان Next را حذف کرد. حتی اگر حذف نشود، بک‌اند لاراول در
وضعیت فعلی روی یک نصب تازه با `migrate --seed` بالا نمی‌آید و چند مسیر پولی
(سفارش، نظر، ورود) رفتار نادرست دارند.

اندازهٔ کد برای درک نسبت کار:

| بخش | فایل | خط |
| --- | --- | --- |
| Next.js (`src/`) | ۲۱۴ | ۳۳٫۸۴۹ خط TS/TSX |
| از آن: پنل مدیریت | ۱۹ صفحه | ۴٫۵۴۸ خط |
| Laravel (`app`, `database`, `routes`) | ۵۵ | ۲٫۹۵۴ خط PHP |
| React (`frontend/src`) | ۲۹ | ۳٫۴۲۶ خط TS/TSX |
| تست‌های Next | ۲۰ فایل | ۳۱۳ مورد `it/test` |
| تست‌های React | ۰ | — |
| endpoint‌های Next | ۳۶ فایل `route.ts` | — |
| مسیرهای API لاراول | ۲۷ endpoint (۲۹ `Route::`) | — |

## ۲. آنچه درست انجام شده

این‌ها را در بازنویسی نگه دارید:

- **قیمت و موجودی فقط سمت سرور.** `CheckoutController` فقط `slug` و `quantity`
  می‌گیرد و قیمت را از دیتابیس می‌خواند؛ فیلدهای قیمتی کلاینت نادیده گرفته
  می‌شوند. همان اصل درست نسخهٔ Next است.
- **تراکنش و قفل ردیف.** ثبت سفارش داخل `DB::transaction` با
  `lockForUpdate()` انجام می‌شود؛ روی MySQL/PostgreSQL از فروش بیش از موجودی
  جلوگیری می‌کند (روی SQLite قفل کل دیتابیس است، پس بی‌اثر ولی بی‌خطر).
- **توکن نشست هش می‌شود.** `auth_sessions.token_hash` فقط SHA-256 توکن را
  نگه می‌دارد؛ توکن خام در مرورگر می‌ماند.
- **Schema قابل انتقال.** بدون enum و بدون `@db.*`؛ JSON برای آرایه‌ها؛
  انتقال به PostgreSQL فقط تغییر اتصال است.
- **جدا شدن فرانت و بک.** پروکسی Vite در توسعه و `VITE_API_URL` در تولید،
  درست طراحی شده‌اند.
- **مستندسازی.** `docs/MIGRATION-LARAVEL.md` ساختار و وضعیت را شفاف نوشته و
  `scripts/smoke-api.mjs` یک آزمون دود سبک و کاربردی است.
- **typecheck و build فرانت سبز است.** (اندازه‌گیری در بخش ۷.)

## ۳. مسدودکننده‌ها (P0) — تا رفع نشوند مهاجرت قابل استفاده نیست

### ۳.۱. دادهٔ اولیهٔ seed در مخزن وجود ندارد

`StoreSeeder` و `ContentSeeder` از `backend/database/seeders/data/` می‌خوانند:

- [`StoreSeeder.php:22`](../backend/database/seeders/StoreSeeder.php#L22)
- [`ContentSeeder.php:23`](../backend/database/seeders/ContentSeeder.php#L23)

این پوشه **در مخزن نیست** (نه در فایل‌های track‌شده و نه روی دیسک). نتیجه:

1. `php artisan migrate --seed` — همان دستوری که در
   [`docs/MIGRATION-LARAVEL.md`](MIGRATION-LARAVEL.md) نوشته شده — روی
   `file_get_contents` خطا می‌دهد (هندلر خطای لاراول warning را به
   `ErrorException` تبدیل می‌کند).
2. `StoreApiTest` و `ContentApiTest` هم در `setUp` همان seeder را صدا می‌زنند،
   پس **کل تست‌های بک‌اند روی یک clone تازه قرمز است**.
3. `scripts/export-content.mjs` فقط `content.json` را می‌سازد و برای
   `products.json` / `categories.json` / `brands.json` هیچ چیزی تولید نمی‌کند؛
   در `package.json` هم ثبت نشده است.

**اصلاح:** فایل‌های `prisma/seed-data/*.json` را به مسیر seeder منتقل کنید (یا
seeder را به همان مسیر بخوانید)، `export-content.mjs` را به یک اسکریپت npm
تبدیل کنید و seeder را در نبود فایل با پیام روشن متوقف کنید، نه دادهٔ خالی.

### ۳.۲. سفارش کاربر واردشده به حسابش وصل نمی‌شود

مسیر `POST /api/checkout` بیرون از گروه `auth.token` است
([`routes/api.php:52`](../backend/routes/api.php#L52))، ولی کنترلر می‌نویسد:

```php
'user_id' => $request->user()?->id,   // CheckoutController.php:99
```

بدون middleware احراز هویت، `user()` همیشه `null` است. یعنی کاربری که وارد شده
سفارش می‌دهد، بعد در «سفارش‌های من» چیزی نمی‌بیند. نسخهٔ Next با
`getCurrentUser()` همین را حل کرده بود.

**اصلاح:** یک middleware احراز هویت «اختیاری» (توکن اگر بود، ست شود) برای
checkout و reviews.

### ۳.۳. ثبت نظر برای کاربر ناشناس، نظر قبلی را بازنویسی می‌کند

```php
Review::updateOrCreate(
    ['product_slug' => $slug, 'user_id' => $user?->id],
    [...]
);   // ProductController.php:124
```

مسیر `POST /products/{slug}/reviews` عمومی است و `$request->user()` همیشه
`null` است؛ پس کلید جست‌وجو همیشه `(slug, null)` است و **هر نظر ناشناس جدید
همان ردیف قبلی را به‌روزرسانی می‌کند**. روی هر محصول فقط یک نظر ناشناس باقی
می‌ماند. از طرف دیگر، هیچ API ادمین برای تأیید نظر وجود ندارد، پس نظرها
همیشه `pending` می‌مانند.

**اصلاح:** `create()` به‌جای `updateOrCreate`، اتصال کاربر با auth اختیاری،
یکتایی `(product_slug, user_id)` برای کاربران واردشده، و صف تأیید در پنل ادمین.

### ۳.۴. هیچ محدودیت نرخی روی OTP و فرم‌ها نیست

در کل `backend/app` و `backend/routes` هیچ `RateLimiter` یا `throttle` تعریف
نشده است. کد OTP پنج‌رقمی است (۱۰۰٬۰۰۰ حالت) و هر درخواست تازه یک کد جدید
می‌سازد که سقف تلاش را ریست می‌کند. مهاجم می‌تواند:

- با درخواست پی‌درپی کد، هزینهٔ پیامک را بالا ببرد (اگر SMS وصل شود)،
- و با ۵ حدس به ازای هر کد، فضای کد را جاروب کند.

نسخهٔ Next برای OTP سقف «۳ درخواست در ۲ دقیقه به ازای شماره» و «۱۰ در ساعت
به ازای IP» داشت و checkout/contact هم محدودیت جدا داشتند
(`src/lib/server/rate-limit.ts`).

**اصلاح:** `RateLimiter::for('otp', ...)` بر اساس `phone + ip`، و
`->middleware('throttle:...')` روی auth، contact، stock-alerts، reviews و
checkout. حتی throttle پیش‌فرض `api` هم کافی نیست چون IP-محور است.

### ۳.۵. هش OTP بدون نمک است

```php
'code_hash' => hash('sha256', $code),   // AuthController.php:36
```

با ۱۰۰٬۰۰۰ حالت ممکن، SHA-256 بدون نمک در چند ثانیه روی یک لپ‌تاپ شکسته
می‌شود. نسخهٔ Next از `sha256(phone:code)` استفاده می‌کرد
(`src/lib/server/auth/otp.ts`).

**اصلاح:** `hash_hmac('sha256', $code, config('app.key') . $phone)` یا
`Hash::make()`؛ مقایسه هم با `hash_equals` (که الان درست است) بماند.

### ۳.۶. کلید idempotency قابل حدس و سراسری است

- فرانت: `idempotencyKey: \`ui-${Date.now()}-${lines.length}\`` —
  [`Checkout.tsx:53`](../frontend/src/pages/Checkout.tsx#L53)
- بک: جست‌وجوی سراسری روی همان کلید و برگرداندن سفارش پیدا‌شده —
  [`CheckoutController.php:37`](../backend/app/Http/Controllers/Api/CheckoutController.php#L37)

کلید از زمان و تعداد اقلام ساخته می‌شود: قابل حدس است و بین کاربران مشترک.
در بدترین حالت (برخورد) پاسخ یک سفارش متعلق به کاربر دیگر برگردانده می‌شود.

**اصلاح:** `crypto.randomUUID()` یک‌بار در شروع تلاش تسویه (نه در هر submit)،
دامنه‌دار کردن کلید به کاربر/نشست، و پاسخ ۴۰۹ در صورت عدم تطابق.

### ۳.۷. با کپی `.env.example`، آدرس API خراب می‌شود

```ts
const BASE = import.meta.env.VITE_API_URL ?? '/api'   // api.ts:7
```

در `frontend/.env.example` مقدار `VITE_API_URL=` خالی است. Vite آن را به
رشتهٔ `""` تبدیل می‌کند و `"" ?? '/api'` برابر `""` است؛ نتیجه: درخواست‌ها
به `/products` می‌روند نه `/api/products` و همه ۴۰۴ می‌شوند.

**اصلاح:** `||` به‌جای `??`، یا حذف خط خالی از فایل نمونه.

انجام می‌شود و مسیر بازگشت/لغو وجود ندارد. تا وقتی درگاه وصل نشده، بهتر است
سفارش‌های `online` موجودی را رزرو نکنند یا وضعیت `awaiting_payment` داشته
باشند.

## ۶. ریسک استراتژیک: سئو

این مهم‌ترین تصمیم پروژه است، مهم‌تر از هر باگ تک‌تک بالا.

نسخهٔ Next سرور-رندر و استاتیک بود: هر محصول متادیتای خودش، JSON-LD محصول و
FAQ، sitemap داینامیک، نقشهٔ سایت دسته/برند، و صفحهٔ آفلاین داشت. در نسخهٔ
جدید:

- `frontend/index.html` **یک** `<title>` و **یک** description برای همهٔ صفحات
  دارد؛ هیچ‌جا `document.title` یا تگ canonical/OG ست نمی‌شود.
- `/category/:slug` و `/brand/:slug` فقط `<Navigate>` به `/shop?category=...`
  هستند؛ یعنی URL‌های ایندکس‌شده و متن سئوی دسته/برند از بین می‌روند.
- `robots.txt` و `sitemap.xml` وجود ندارند (`frontend/public/` هم ساخته نشده).
- محصول و مقاله فقط سمت کلاینت رندر می‌شوند: LCP دیرتر، ایندکس ضعیف‌تر، و
  مسیر ناموجود هم HTTP 200 برمی‌گرداند (soft 404).

برای یک فروشگاه لوازم خانگی که ترافیکش عمدتاً از جستجوی فارسی می‌آید، این
به‌تنهایی می‌تواند دلیل شکست مهاجرت باشد. گزینه‌ها:

| گزینه | مزیت | هزینه |
| --- | --- | --- |
| **A.** Next بماند، فقط API به لاراول منتقل شود | حفظ کامل SEO و سرمایهٔ موجود؛ لاراول منبع داده | دو runtime و دو deploy |
| **B.** Laravel + Inertia + SSR | یک deploy، SSR واقعی، اکوسیستم لاراول | بازنویسی لایهٔ فرانت و از دست رفتن کامپوننت‌های Next |
| **C.** SPA + prerender (مثل `vite-ssg` / `react-snap`) + `react-helmet-async` | حداقل تغییر، SEO صفحات ثابت و محصولات | محصولات داینامیک باید prerender زمان build شوند؛ محدودیت مقیاس |
| **D.** SPA خالص + قبول افت SEO | ساده‌ترین | فقط اگر ترافیک ارگانیک مهم نباشد |

**توصیه:** اگر SEO اولویت است، A یا B. اگر تیم می‌خواهد همین SPA بماند،
حداقل C را جدی بگیرید و صفحات دسته/برند را به مسیر مستقل برگردانید.

## ۷. کیفیت کد و تجربهٔ کاربری (P2)

**کلاینت API** ([`api.ts`](../frontend/src/lib/api.ts)):

- `JSON.parse(text)` بدون `try/catch` — پاسخ HTML (۵۰۰، پروکسی، CORS) باعث
  خطای مبهم می‌شود.
- اولویت پیام خطا: `data.error || data.message` قبل از `data.errors`؛ چون
  لاراول برای خطای اعتبارسنجی همیشه `message` انگلیسی دارد، پیام فارسی
  فیلدها هرگز دیده نمی‌شود.
- هیچ مدیریت ۴۰۱ سراسری، timeout یا `AbortController` نیست.

**احراز هویت:**

- `signOut` فقط `localStorage` را پاک می‌کند و `/auth/logout` را صدا نمی‌زند؛
  نشست سرور تا ۳۰ روز معتبر می‌ماند
  ([`AuthContext.tsx:43`](../frontend/src/context/AuthContext.tsx#L43)).

## ۱۰. به‌روزرسانی: باگ‌های رفع‌شده (دور دوم)

در این دور، موارد P0 و چند باگ کلاینت رفع شدند و بک‌اند با PHP 8.4 portable
اجرا و تست شد.

**رفع‌شده در بک‌اند:**

- دادهٔ seed در `backend/database/seeders/data/` قرار گرفت (دسته، برند، محصول
  و `content.json` برای مقالات/پرسش‌ها/حقوقی/باشگاه). ریشهٔ گم‌شدن فایل‌ها
  پیدا شد: الگوی `data/` در `.gitignore` ریشه، هر پوشهٔ هم‌نام را در کل مخزن
  نادیده می‌گرفت. به `/data/` تغییر کرد.
- seederها در نبود فایل با پیام روشن متوقف می‌شوند و `migrate:fresh --seed`
  روی نصب تازه موفق است.
- `auth.token:optional` اضافه شد و روی checkout، نظرات و هشدار موجودی اعمال
  شد؛ سفارش کاربر واردشده به حسابش وصل می‌شود و در `/api/account/orders`
  دیده می‌شود.
- نظر مهمان دیگر نظر قبلی را بازنویسی نمی‌کند (برای کاربر واردشده، ویرایش
  همان نظر خودش با بازگشت به صف تأیید).
- محدودیت نرخ برای OTP (۳ در ۲ دقیقه به ازای شماره، ۳۰ در ساعت به ازای IP —
  سقف IP عمداً بالاتر است چون کاربران ایرانی پشت NAT اپراتور IP مشترک دارند)،
  checkout، تماس، نظرات و هشدار موجودی.
- هش OTP به HMAC-SHA256 با کلید برنامه و شماره به‌عنوان نمک تغییر کرد و
  کدهای فعال قبلی با هر درخواست تازه باطل می‌شوند.
- کلید idempotency به UUID سمت کلاینت تغییر کرد و به صاحب سفارش (کاربر یا
  شمارهٔ مهمان) محدود شد؛ برخورد کلید پاسخ ۴۰۹ می‌دهد.
- نرمال‌سازی شماره در checkout، پیگیری سفارش، تماس و هشدار موجودی؛ پیگیری
  سفارش شمارهٔ `+98` و حروف کوچک را هم می‌پذیرد.
- پیام‌های اعتبارسنجی فارسی (`lang/fa/validation.php`) و `APP_LOCALE=fa`.
- هدرهای امنیتی پایه روی همه پاسخ‌ها؛ CORS در production فقط `FRONTEND_URL`.
- حالت توسعهٔ OTP از `env()` مستقیم به `config/auth_otp.php` منتقل شد،
  پیش‌فرض `false` است و در production هرگز کد برنمی‌گردد.

**رفع‌شده در فرانت:**

- `VITE_API_URL` خالی دیگر به آدرس بدون `/api` تبدیل نمی‌شود.
- خطای JSON نامعتبر و پاسخ HTML مدیریت می‌شود؛ خطاهای اعتبارسنجی فیلدها بر
  پیام عمومی انگلیسی اولویت دارند.
- پاسخ ۴۰۱ نشست را در کل برنامه پاک می‌کند و خروج، `/auth/logout` را صدا
  می‌زند.
- هزینهٔ ارسال و روش‌های پرداخت از API خوانده می‌شوند (تنظیمات پنل و روش‌های
  غیرفعال).
- کلید idempotency تسویه با `crypto.randomUUID()`.
- صفحهٔ حساب تا آماده‌شدن نشست رندر نمی‌شود و خطای دریافت سفارش را نشان می‌دهد.
- ErrorBoundary سراسری؛ تعداد کالای هیرو از کاتالوگ خوانده می‌شود.

**بدون تغییر باقی مانده:** درگاه پرداخت و callback، وبهوک/اتوماسیون،
رمزنگاری تنظیمات، بخش‌های دیگر پنل (کوپن، مشتریان، تنظیمات، گزارش فروش،
اتوماسیون)، مقایسه و علاقه‌مندی، زیرصفحه‌های حساب، جستجوی خودکار، PWA و سئوی
فنی (متادیتای هر صفحه، sitemap، robots، JSON-LD). جزئیات در بخش‌های ۵، ۶ و ۱۱.

## ۱۱. پنل مدیریت لاراول (دور سوم)

پنل مدیریت با تمرکز بر «مدیریت کاتالوگ و سفارش‌ها بدون دست‌زدن به کد» اضافه شد.

**API (همه پشت `auth.token` + `admin`):**

- آمار داشبورد، محصولات (فهرست، جزئیات، ساخت، ویرایش جزئی، حذف)، سفارش‌ها
  (فهرست، جزئیات، تغییر وضعیت/رهگیری/یادداشت)، نظرات (صف و تأیید/رد) و گزارش
  فعالیت.
- ویرایش محصول فقط فیلدهای ارسالی را عوض می‌کند و نامک پس از ساخت قفل است
  (نظرها و سابقهٔ سفارش با نامک ارجاع دارند).
- حذف کالای دارای سابقهٔ سفارش ۴۰۹ می‌دهد؛ برای پنهان‌کردن، کالا غیرفعال
  می‌شود.
- انتقال وضعیت سفارش اعتبارسنجی می‌شود؛ لغو سفارش موجودی اقلام را فقط یک‌بار
  برمی‌گرداند.
- تأیید/رد نظر، `rating` و `review_count` محصول را از نظرهای تأییدشده دوباره
  حساب می‌کند.
- هر تغییر با `App\Support\Audit` در `audit_logs` ثبت می‌شود (کاربر، اقدام،
  موجودیت، جزئیات تغییر، IP و مرورگر) و در `/admin/audit` قابل مشاهده است.

**فرانت (React):** مسیرهای `/admin` (داشبورد)، `/admin/products`،
`/admin/orders`، `/admin/reviews` و `/admin/audit` با محافظ نقش در سمت کلاینت
(سرور هم مستقل بررسی می‌کند) و chunk جداگانه؛ باندل فروشگاه برای مشتریان
افزایش پیدا نکرد (۲۶۰٫۸ کیلوبایت / ۷۶٫۵ گزیپ).

**آزمون:** ۶ تست جدید برای دسترسی (۴۰۱/۴۰۳)، ساخت و ویرایش جزئی، منع حذف کالای
دارای سفارش، انتقال وضعیت و برگشت موجودی، تأیید نظر و محاسبهٔ امتیاز، و ثبت
لاگ حسابرسی. مجموع تست‌ها: ۳۲ (۲۰۱ assertion).
