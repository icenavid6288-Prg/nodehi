## تصمیم‌های معماری و دلیل آن‌ها

### ۱. Server Components به‌عنوان پیش‌فرض

فقط کامپوننتی که واقعاً تعامل نیاز دارد، `'use client'` می‌گیرد. نتیجه اندازه‌بندی
خروجی بیلد نشان می‌دهد چرا این تفکیک مهم است:

| مسیر | حجم باندل صفحه | دلیل |
| --- | --- | --- |
| `/about`, `/faq`, `/terms` | ۱۹۹ بایت | کاملاً سرورساید — فقط HTML |
| `/product/[slug]` | ۵.۲۵ کیلوبایت | فقط گالری و دکمه‌های اکشن کلاینتی هستند |
| `/shop` | ۱۰.۴ کیلوبایت | پنل فیلتر و مرتب‌سازی کلاینتی |
| `/compare` | ۶.۰۳ کیلوبایت | جدول تعاملی |
| `/account/wishlist` | ۵.۶۴ کیلوبایت | وابسته به وضعیت محلی |

صفحات محتوایی و محصول از باندل جاوااسکریپت تقریباً صفر بهره می‌برند.

### ۲. وضعیت فیلتر در URL، نه در state

فیلترها در `state` ری‌اکت نگه‌داری **نمی‌شوند**؛ در query string نوشته می‌شوند:

```
/shop?category=refrigerator&brand=samsung,lg&energy=A%2B%2B&minPrice=30000000&sort=price-asc
```

مزایا:

- **سئو:** هر ترکیب فیلتر یک URL یکتاست و می‌تواند در نتایج گوگل بیاید. صفحات
  پرترکیب با `noIndex` علامت‌گذاری می‌شوند تا محتوای تکراری ایجاد نشود.
- **اشتراک‌گذاری:** کاربر می‌تواند لینک نتیجه فیلترشده را برای دیگری بفرستد.
- **مرورگر:** دکمه Back و Forward دقیقاً همان‌طور که انتظار می‌رود کار می‌کند.
- **بازگشت به صفحه:** با رفرش، فیلترها حفظ می‌شوند.

منطق تبدیل این پارامترها در یک فایل مشترک (`src/lib/filters.ts`) قرار دارد تا
کامپوننت سرور و کلاینت هرگز از هم جدا نیفتند. تست رفت‌وبرگشت این تبدیل در
`src/lib/filters.test.ts` وجود دارد.

### ۳. شمارش فیلترها با نادیده گرفتن فیلتر خودشان

در فیلتر چندوجهی، اگر شمارش هر گروه را از نتیجه نهایی بگیریم، انتخاب «یخچال»
باعث می‌شود بقیه دسته‌ها صفر نشان داده شوند و کاربر فکر کند خالی هستند.

پیاده‌سازی درست: برای شمارش هر گروه، همان فیلترها **منهای فیلتر آن گروه** اعمال
می‌شود.

```ts
const brandFacets   = buildFacets(queryProducts({ ...filters, brands: [] }))
const colorFacets   = buildFacets(queryProducts({ ...filters, colors: [] }))
const energyFacets  = buildFacets(queryProducts({ ...filters, energyRatings: [] }))
const categoryList  = queryProducts({ ...filters, categories: [] })
```

نتیجه مشاهده‌شده: با انتخاب «یخچال و فریزر»، سایر دسته‌ها اعداد واقعی خود را
نشان می‌دهند (لباسشویی ۶، ظرفشویی ۳، تلویزیون ۳ …) نه صفر.

### ۴. بدون وابستگی برای تقویم شمسی

تبدیل تاریخ با `Intl.DateTimeFormat('fa-IR-u-ca-persian')` انجام می‌شود که در
موتور جاوااسکریپت تعبیه شده است. کتابخانه‌هایی مثل `moment-jalaali` یا
`date-fns-jalali` حدود ۴۰ تا ۷۰ کیلوبایت به باندل اضافه می‌کنند؛ برای نمایش
تاریخ — که تنها نیاز این پروژه است — این هزینه توجیه ندارد.

### ۵. بدون وابستگی برای آیکون

تمام آیکون‌ها SVG درون‌خطی هستند (`src/components/ui/appliance-icon.tsx` و
بقیه کامپوننت‌ها). نه پکیج آیکون اضافه می‌شود و نه برای هر آیکون یک درخواست
شبکه‌ای زده می‌شود.

### ۶. توکن‌های برند در یک فایل واحد

`src/config/brand.ts` تنها منبع حقیقت برای رنگ، فونت، اطلاعات تماس و شعبه‌هاست.
`tailwind.config.ts` این فایل را import می‌کند، بنابراین تغییر یک رنگ در آن
فایل در تمام کامپوننت‌ها اعمال می‌شود. هیچ مقدار hex ای جای دیگری هارد‌کد نشده.

### ۷. جانگهدار تصویر به‌جای تصویر شکسته

هر محصول آرایه `images` دارد. تا زمانی که خالی است، `ProductImage` یک گرادیان
هم‌رنگ دسته‌بندی همراه آیکون همان لوازم خانگی نمایش می‌دهد. پس از بارگذاری عکس‌های
واقعی روی مخزن آروان/لیارا، فقط فیلد `images` پر می‌شود و هیچ کدی تغییر نمی‌کند.

## لایه داده — قرارداد تعویض با Prisma

کامپوننت‌ها **هرگز** مستقیم به `products.ts` دسترسی ندارند؛ همیشه از توابع
`src/lib/data/queries.ts` عبور می‌کنند:

```ts
queryProducts(filters)      // فیلتر + مرتب‌سازی + جستجو
buildFacets(list)           // گزینه‌های فیلتر با شمارش
relatedProducts(product)    // محصولات مشابه
bestSellers(n)              // پرفروش‌ترین‌ها
discountedProducts(n)       // تخفیف‌دارها
readyToShipProducts(n)      // آماده ارسال
searchSuggestions(q)        // پیشنهاد خودکار جستجو
categoryCounts()            // تعداد کالای هر دسته
```

برای مهاجرت به دیتابیس، فقط بدنه همین توابع را به کوئری Prisma تغییر دهید و
`async` کنید. کامپوننت‌های مصرف‌کننده فقط به `await` نیاز پیدا می‌کنند.

### نکته حیاتی واحد پول

کاتالوگ فعلی قیمت را به **تومان** نگه می‌دارد (چون مستقیم نمایش داده می‌شود).
دیتابیس همه مبالغ را به **ریال** ذخیره می‌کند (عدد صحیح، بدون اعشار). در مرز
این دو لایه تبدیل لازم است:

```ts
const tomanToRial = (toman: number) => toman * 10
const rialToToman = (rial: number) => Math.round(rial / 10)
```

این تبدیل را در یک ماژول واحد متمرکز کنید. اگر در چند نقطه پخش شود، دیر یا زود
یک جا فراموش می‌شود و قیمت ده برابر غلط نمایش داده می‌شود.

## احراز هویت (مرحله بعد)

ورود پیامکی برای مخاطب ایرانی از ورود با رمز عبور مناسب‌تر است، چون کاربر
معمولاً رمز را فراموش می‌کند و شماره همراه تقریباً همیشه در دسترس است.

```
کاربر شماره را وارد می‌کند
   ↓  POST /api/auth/otp/request   (نرخ: ۳ درخواست در ۱۰ دقیقه به ازای هر شماره)
پیامک با کد ۶ رقمی از طریق کاوه‌نگار
   ↓  کد در جدول OtpCode به‌صورت هش‌شده ذخیره می‌شود، عمر ۲ دقیقه
کاربر کد را وارد می‌کند
   ↓  POST /api/auth/otp/verify    (حداکثر ۵ تلاش)
صدور JWT و ساخت Session در دیتابیس
```

نکات امنیتی:

- کد پیامکی **هرگز به‌صورت متن ساده** ذخیره نمی‌شود؛ هش می‌شود.
- نرخ درخواست هم روی شماره و هم روی IP محدود می‌شود.
- برای نقش‌های `ADMIN`، `ACCOUNTANT` و `OPERATOR`، احراز هویت دو مرحله‌ای
  (`twoFactorEnabled`) اجباری است.
- پس از پنج تلاش ناموفق، حساب موقتاً قفل می‌شود (`lockedUntil`).

## استراتژی کش

| داده | محل | مدت اعتبار | دلیل |
| --- | --- | --- | --- |
| دارایی‌های `_next/static` | مرورگر + CDN | یک سال، `immutable` | نام فایل شامل هش نسخه است |
| صفحه محصول | ISR | ۱۰ دقیقه | قیمت و موجودی باید تازه بمانند |
| صفحه دسته‌بندی | ISR | ۵ دقیقه | تعادل بین تازگی و بار سرور |
| فیلتر پیشرفته | Redis | ۲ دقیقه | کوئری سنگین، نتایج پرتکرار |
| موجودی انبار | بدون کش | — | نادرستی موجودی مستقیماً به فروش کالای ناموجود می‌انجامد |
| صفحه آفلاین | Service Worker | نامحدود | تجربه بهتر در قطعی شبکه |

قاعده کلی: **هرچه داده به پول نزدیک‌تر است، کش کوتاه‌تر.** موجودی و قیمت را
کش نکنید؛ متن مقاله و تصاویر را با خیال راحت کش کنید.

## مرزهای اعتماد (Trust Boundaries)

| لایه | چه چیزی را باور نکنید |
| --- | --- |
| ورودی URL | `searchParams` — همیشه اعتبارسنجی و محدود شود (طول، بازه، مقدار مجاز) |
| فرم‌های کلاینت | اعتبارسنجی کلاینت فقط برای تجربه کاربری است؛ در سرور **تکرار** شود |
| وضعیت `localStorage` | قابل دستکاری کاربر است — هرگز مبنای محاسبه قیمت نهایی نباشد |
| وب‌هوک‌های ورودی | بدون بررسی امضای HMAC پردازش نشوند |
| بازگشت از درگاه پرداخت | مبلغ و وضعیت باید از API درگاه **استعلام** شود، نه از query string |

آخرین مورد مهم‌ترین است: هرگز به پارامترهای بازگشتی از درگاه اعتماد نکنید.
پس از بازگشت کاربر، سرور باید مستقیماً تراکنش را از API درگاه استعلام کند و
تنها در صورت تأیید، سفارش را پرداخت‌شده علامت بزند.
