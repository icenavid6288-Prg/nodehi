# نودهی — فروشگاه اینترنتی لوازم خانگی

فروشگاه آنلاین لوازم خانگی با تمرکز بر **سرعت**، **سئوی فارسی** و **تجربه کاربری راست‌به‌چپ**.

این مخزن یک فروشگاه **کامل و اجراشدنی** است: صفحات فروشگاه، پنل کاربری، پنل مدیریت،
دیتابیس واقعی با migration، ورود با شماره همراه و کد یک‌بارمصرف، ثبت سفارش روی دیتابیس
و سئوی فنی. دیتابیس پیش‌فرض یک فایل SQLite است تا بدون هیچ سرویس بیرونی بالا بیاید و
اسکیما طوری نوشته شده که انتقال به PostgreSQL در تولید فقط تغییر `provider` باشد.
آنچه هنوز نیاز به کلید بیرونی دارد (درگاه پرداخت، پیامک، ایمیل) با راهنمای اتصال در
`docs/INTEGRATIONS.md` آمده و تا فعال شدنش، مسیرهای مربوطه رفتار امن و شفاف دارند.

## شروع سریع

```bash
npm install
cp .env.example .env   # آدرس دیتابیس و تنظیمات ورود
npm run db:migrate     # ساخت جداول و اجرای migration‌ها
npm run db:seed        # کاتالوگ (کالا، دسته، برند)، کدهای تخفیف، حساب مدیر، چند نظر نمونه و پیش‌فرض درگاه‌ها
npm run dev -- -p 3000
```

سپس <http://localhost:3000> را باز کنید.

**دیتابیس:** یک فایل SQLite (`prisma/dev.db`) که خودکار ساخته می‌شود — نیازی به نصب
PostgreSQL، Docker یا سرویس بیرونی نیست. برای کلید API هم لازم نیست چیزی تنظیم کنید؛
همه مسیرها بدون کلید هم رفتار امن و مشخص دارند.

**ورود:** وارد `/login` شوید و شماره همراه بگذارید. چون سرویس پیامک متصل نیست، با
`AUTH_OTP_DEV_MODE=1` کد ورود در همان صفحه و در پاسخ API نشان داده می‌شود. برای
رسیدن به پنل مدیریت، با شماره‌ای که در `db:seed` نقش admin گرفته وارد شوید
(پیش‌فرض `09120000000`). سه راه ورود به پنل هست: لینک «ورود کارکنان» در فوتر،
دکمه «پنل مدیریت» در نوار کناری حساب کاربری، یا `/login?next=/admin` که پس از ورود
مستقیم به همان صفحه می‌برد.

**تنظیمات پنل:** متن اعلان، حالت تعمیرات، بنر تبلیغاتی، کلید API پیامک و وبهوک
اتوماسیون از خود پنل مدیریت (مسیرهای `/admin/settings`, `/admin/sms`,
`/admin/payments`, `/admin/automation`) قابل تغییرند و اولویتشان بر متغیر محیطی است.
برای رمزنگاری مقدارهای حساس، `SETTINGS_ENCRYPTION_KEY` (۳۲ بایت،
`openssl rand -hex 32`) را در محیط تولید تنظیم کنید؛ بدون آن مقدارها متن ساده ذخیره
می‌شوند و پنل هشدار می‌دهد.

```bash
npm run typecheck   # بررسی نوع‌ها
npm run lint        # بررسی قواعد کد
npm test            # اجرای تست‌ها (۳۳۹ تست)
npm run build       # بیلد تولید
npm start           # اجرای نسخه تولید
npm run clean       # پاک‌کردن خروجی .next (وقتی صفحه‌ها خطا می‌دهند)
npm run reinstall   # پاک‌کردن داده‌ها و نصب دوباره از صفر (با SEED_ADMIN_PHONE)
npm run pack:host   # ساخت nodehi-deploy.zip تمیز برای انتقال به هاست (بدون دیتابیس و node_modules)
npm run doctor      # بررسی آمادگی استقرار: بیلد، .env، دیتابیس، مهاجرت‌ها، محل پروژه
```

> **انتقال با زیپ به هاست:** `node_modules`، `.next`، `.env` و `prisma/dev.db` را داخل زیپ
> نگذارید؛ روی هاست `npm install` → `npm run setup` → `npm run build && npm start` را اجرا
> کنید. جزئیات و راه بازگرداندن نصب: [`docs/SETUP.md`](docs/SETUP.md#انتقال-با-زیپ-به-هاست-بدون-git).

> **۴۰۴ روی هاست اشتراکی:** باز کردن زیپ داخل `public_html` باعث ۴۰۴ روی همهٔ آدرس‌ها
> می‌شود، چون وب‌سرور فایل استاتیک سرو می‌کند و Next به پروسهٔ Node زنده نیاز دارد.
> پروژه را هم‌سطح `public_html` ببرید، در پنل Node.js App بسازید و Startup file را
> `server.js` بگذارید. راهنمای گام‌به‌گام: [`docs/SETUP.md`](docs/SETUP.md#هاست-اشتراکی-و-۴۰۴-بعد-از-آپلود-زیپ).

> ⚠️ اگر سرور توسعه در حال اجراست، پیش از `npm run build` آن را متوقف کنید؛ هر دو
> از پوشه `.next` استفاده می‌کنند و اجرای هم‌زمان بیلد، سرور توسعه را خراب می‌کند.
> `npm run dev` خودش دو حالت خرابی را می‌گیرد: خروجی بیلد تولیدی را پیش از شروع پاک
> می‌کند و اگر سایت همین حالا روی همان پورت بالا باشد، فقط آدرس را نشان می‌دهد و سرور
> دومی بالا نمی‌آورد (اگر پورت را برنامه دیگری گرفته باشد، با پیام روشن متوقف می‌شود).

## شخصی‌سازی برند

تمام رنگ‌ها، فونت، اطلاعات تماس، شعبه‌ها و شبکه‌های اجتماعی در **یک فایل** تعریف شده‌اند:

```ts
// src/config/brand.ts
colors: {
  primary:   { DEFAULT: '#0F2A43' },  // سرمه‌ای — رنگ غالب
  secondary: { DEFAULT: '#12B5A5' },  // فیروزه‌ای — مکمل
  accent:    { DEFAULT: '#FF6B35' },  // نارنجی — فقط CTA و تخفیف
}
```

`tailwind.config.ts` این مقادیر را می‌خواند، بنابراین تغییر یک رنگ در `brand.ts`
در تمام کامپوننت‌ها اعمال می‌شود. هیچ رنگ hex ای در جای دیگری هارد‌کد نشده است.

## نکات پیاده‌سازی

**کاتالوگ روی دیتابیس است و از پنل مدیریت می‌شود.** کالا، دسته و برند در جدول‌های
`Product`/`Category`/`Brand` می‌نشینند و افزودن یا حذف کالا دیگر نیازی به ویرایش کد
و انتشار دوباره ندارد. سه تصمیم اینجا مهم است:

- **آرایه‌ها JSON متنی‌اند.** نکته‌ها، مشخصات، تصاویر، تگ‌ها و کالاهای مرتبط به‌صورت
  متن JSON ذخیره می‌شوند، چون SQLite آرایه اسکالر ندارد و اسکیما عمداً «بدون `@db.*`
  و بدون enum» است تا انتقال به PostgreSQL فقط تغییر `provider` باشد.
- **حذف، دو حالت دارد.** کالایی که سابقه سفارش دارد حذف قطعی نمی‌شود (۴۰۹) و باید
  «غیرفعال» شود؛ `isActive: false` کالا را از فروشگاه بیرون می‌برد ولی گزارش‌های فروش
  و سفارش‌های قدیمی را سالم نگه می‌دارد. کالای بدون سابقه کاملاً حذف می‌شود تا اشتباه
  در ورود کالا قابل جبران باشد.
- **ویرایش فقط تفاوت‌ها را می‌فرستد.** فرم ویرایش، حالت فعلی را با حالت اولیه مقایسه
  می‌کند و تنها فیلدهای تغییرکرده را PATCH می‌کند؛ همین قاعده از پاک شدن بی‌قصد ابعاد،
  تصاویر یا قیمت جلوگیری می‌کند. سرور هم ویژگی‌های غایب را از مقدار قبلی نگه می‌دارد.

**قیمت فقط روی سرور محاسبه می‌شود.** `POST /api/checkout` تنها نامک محصول و تعداد را
از مرورگر می‌پذیرد و قیمت را از کاتالوگ می‌خواند. هر فیلد قیمتی که کلاینت بفرستد
(مثل `price` یا `lineTotal`) نادیده گرفته می‌شود، پس دستکاری قیمت در DevTools بی‌اثر
است. ریاضیِ سبد و روش‌های ارسال در `src/lib/commerce.ts` یک بار نوشته شده و هم UI و هم
API از آن می‌خوانند تا قیمت نمایش‌داده‌شده هرگز با قیمت نهایی اختلاف نداشته باشد —
هزینه هر روش ارسال هم از همین ماژول خوانده می‌شود، نه از ورودی مرورگر.

**ورود بدون رمز عبور.** ثبت‌نام و ورود یک مسیر واحد است: شماره همراه → کد یک‌بارمصرف
→ ساخت خودکار حساب. کد هرگز به‌صورت خام ذخیره نمی‌شود (هش SHA-256 با نمک شماره) و
توکن نشست هم در دیتابیس فقط به شکل هش می‌ماند؛ بنابراین لو رفتن نسخه پشتیبان، حساب‌ها
را باز نمی‌کند. کد یک‌بارمصرف سقف تلاش دارد، با هر ارسال تازه باطل می‌شود و فقط یک بار
مصرف می‌شود.

**کنترل دسترسی سمت سرور است، نه در رابط کاربری.** پنل مدیریت و پنل کاربری هر دو
پیش از رندر در لایه سرور بررسی می‌شوند؛ پنهان کردن دکمه در مرورگر امنیت نیست. کاربر
بدون نقش مدیریتی به‌جای پیام «دسترسی ندارید»، همان صفحه ۴۰۴ سایت را می‌بیند تا وجود
مسیر مدیریت افشا نشود. هر تغییر مدیریتی هم در جدول `AuditLog` با نام کاربر ثبت می‌شود.

**کشوی منوی موبایل روی `document.body` رندر می‌شود.** هدر `backdrop-blur` دارد و
`backdrop-filter` برای فرزندان `position: fixed` یک containing block می‌سازد؛ پس اگر
کشو داخل هدر بماند، `fixed inset-0` به‌جای کل صفحه فقط به کادر هدر بسته می‌شود و
منو عملاً استفاده‌ناپذیر می‌شود. کامپوننت `mobile-menu.tsx` با `createPortal` بیرون
هدر رندر می‌شود — این تصمیم را برنگردانید.

**مودیفایر شفافیت فقط با مضرب‌های ۵ کار می‌کند.** مقیاس پیش‌فرض `opacity` در
Tailwind شامل ۵، ۱۰، ۱۵، ۲۰ و ... است؛ کلاسی مثل `bg-primary/8` یا `bg-white/12`
هیچ CSS ای تولید نمی‌کند و عنصر بی‌رنگ می‌ماند (یا رنگ پیش‌فرض مرورگر را می‌گیرد،
که روی زمینه تیره فاجعه است). برای مقادیر دقیق‌تر از سینتکس دلخواه استفاده کنید:
`bg-primary/[0.08]`.

**وبهوک‌ها امضاشده‌اند.** مسیر `api/webhooks/order-paid` بدون امضای معتبر HMAC
پاسخی نمی‌دهد و بدون تنظیم کلید، با ۵۰۳ بسته می‌ماند تا هرگز در حالت بدون محافظت
اجرا نشود. ارسال رویداد به n8n هم «آتش و فراموش» است تا خرابی اتوماسیون، ثبت سفارش
را متوقف نکند — اما بی‌ردپا هم نیست: هر تلاش با وضعیت `sent`/`failed`/`skipped` و کد
پاسخ HTTP در جدول رویدادها ثبت می‌شود و از `/admin/automation` با همان بدنه و همان
امضا دوباره فرستاده می‌شود، پس سمت n8n پردازش تکراری رخ نمی‌دهد.

**تنظیمات پنل یک فهرست بسته است.** کلیدهای مجاز در `src/lib/server/settings.ts`
تعریف می‌شوند، نه در دیتابیس؛ پس یک ردیف ناشناخته یا دستکاری‌شده نمی‌تواند رفتار
سایت را عوض کند. ترتیب خواندن مقدار: دیتابیس → متغیر محیطی → پیش‌فرض کد، و همین
باعث می‌شود سایت بدون هیچ کلید API هم بالا بیاید. مقدارهای نوع `secret` با
AES-256-GCM رمزنگاری می‌شوند، هرگز به مرورگر برگردانده نمی‌شوند (پاسخ فقط
`hasValue` دارد) و لاگ حسابرسی هم فقط نام کلیدهای تغییر‌یافته را ثبت می‌کند.

**فیلتر پیشرفته بدون جاوااسکریپت سنگین.** وضعیت فیلترها در URL نگه‌داری می‌شود
(`/shop?category=refrigerator&brand=samsung&energy=A++`). نتیجه: هر ترکیب فیلتر یک
لینک قابل اشتراک و قابل خزش است و دکمه Back مرورگر درست کار می‌کند.

**شمارش گزینه‌های فیلتر (facet) به‌درستی محاسبه می‌شود.** هر گروه با نادیده گرفتن
فیلتر خودش شمرده می‌شود؛ بنابراین وقتی «یخچال» انتخاب شده، سایر دسته‌ها هم تعداد
واقعی خود را نشان می‌دهند نه صفر.

**تقویم شمسی بدون وابستگی.** از `Intl.DateTimeFormat('fa-IR-u-ca-persian')` استفاده
می‌شود؛ حدود ۴۰ کیلوبایت کمتر از کتابخانه‌های تاریخ شمسی در باندل.

**آیکون‌ها SVG درون‌خطی هستند.** نه وابستگی آیکون‌پک اضافه می‌شود و نه درخواست
شبکه‌ای برای هر آیکون زده می‌شود.

**جانگهدار تصویر برندشده.** تا بارگذاری عکس واقعی محصولات، هر کارت یک گرادیان
هم‌رنگ دسته‌بندی با آیکون نمایش می‌دهد؛ بنابراین هیچ تصویر شکسته‌ای وجود ندارد.
