# امنیت فروشگاه نودهی

این سند دو بخش دارد: **آنچه همین حالا پیاده شده** و **آنچه پیش از انتشار باید
تکمیل شود**. چک‌لیست انتها را در هر انتشار مرور کنید.

---

## ۱. آنچه در این نسخه پیاده شده است

### هدرهای امنیتی

در `next.config.mjs` روی تمام مسیرها اعمال می‌شود:

| هدر | مقدار | کارکرد |
| --- | --- | --- |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains; preload` | مرورگر را برای دو سال به HTTPS قفل می‌کند |
| `X-Content-Type-Options` | `nosniff` | جلوگیری از تشخیص نوع فایل توسط مرورگر (حمله MIME sniffing) |
| `X-Frame-Options` | `SAMEORIGIN` | جلوگیری از Clickjacking در iframe |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | جلوگیری از نشت آدرس کامل صفحات داخلی |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(self)` | بستن دسترسی‌های سخت‌افزاری بی‌استفاده |
| `Content-Security-Policy-Report-Only` | سیاست محدودکننده | ابتدا گزارش، سپس اجباری |

**نکته مهم:** CSP فعلی در حالت **Report-Only** است. پس از پیکربندی دامنه‌های
نهایی (درگاه پرداخت، چت‌بات، مخزن تصاویر)، گزارش‌های نقض را بررسی و دامنه‌های
لازم را اضافه کنید، سپس هدر را از `Content-Security-Policy-Report-Only` به
`Content-Security-Policy` تغییر دهید تا اجباری شود.

فعال‌سازی اجباری CSP بدون بررسی قبلی، سایت را از کار می‌اندازد.

### جلوگیری از XSS

- React به‌صورت پیش‌فرض تمام مقادیر را escape می‌کند. در این پروژه **هیچ**
  استفاده‌ای از `dangerouslySetInnerHTML` روی داده کاربر وجود ندارد.
- تنها مورد استفاده، کامپوننت `JsonLd` است که داده آن از توابع کنترل‌شده
  `src/lib/seo.ts` می‌آید، نه از ورودی کاربر. علاوه بر آن، نویسه `<` در خروجی
  به `\u003c` تبدیل می‌شود تا امکان بستن تگ `script` وجود نداشته باشد:

```ts
dangerouslySetInnerHTML={{ __html: JSON.stringify(data).replace(/</g, '\\u003c') }}
```

- React به‌صورت پیش‌فرض هیچ ورودی کاربر را به‌عنوان HTML تفسیر نمی‌کند.

### جلوگیری از تزریق در لایه داده

کاتالوگ محصولات هنوز درون‌حافظه است، اما بخش عملیاتی (کاربر، نشست، سفارش، آدرس،
نظر، کد تخفیف، پیام، هشدار موجودی) روی دیتابیس و از طریق Prisma خوانده و نوشته
می‌شود. همه کوئری‌ها با API ساختارمند Prisma نوشته شده‌اند، پس ورودی کاربر هرگز
به متن SQL نمی‌چسبد. دو قاعده الزامی:

1. **همیشه از Prisma استفاده کنید، نه کوئری خام.** Prisma پارامترها را
   ساختارمند ارسال می‌کند و کوئری دستکاری‌شده ممکن نیست.
2. اگر ناچار به `$queryRaw` شدید، **حتماً** از tagged template استفاده کنید:

```ts
// ✅ درست — پارامتر به‌صورت امن ارسال می‌شود
await prisma.$queryRaw`SELECT * FROM "Product" WHERE id = ${productId}`

// ❌ هرگز — امکان تزریق
await prisma.$queryRawUnsafe(`SELECT * FROM "Product" WHERE id = '${productId}'`)
```

### اعتبارسنجی ورودی URL

`src/lib/filters.ts` تمام پارامترهای آدرس را اعتبارسنجی و محدود می‌کند، چون
کاربر می‌تواند هر مقداری را دستی وارد کند:

```ts
q: first(params.q).slice(0, 100)                              // سقف طول
sort: SORT_KEYS.includes(raw) ? raw : 'relevance'             // مقدار از فهرست مجاز
page: Number.isFinite(p) && p > 0 ? p : 1                     // اصلاح مقدار منفی
perPage: Math.min(48, Math.max(8, n))                         // میانه‌گیری در بازه
```

مقدار `sort` از یک فهرست سفید می‌آید، نه اینکه مستقیم در کوئری استفاده شود.
`page=-5` به صفحه ۱ اصلاح می‌شود (این مورد در تست پوشش داده شده است).

### جلوگیری از حمله ربات در فرم‌ها

فرم تماس شامل یک فیلد تله (honeypot) است که برای کاربر نامرئی است. ربات‌ها آن
را پر می‌کنند و درخواست رد می‌شود:

```tsx
<div className="hidden" aria-hidden="true">
  <input id="contact-website" name="website" tabIndex={-1} autoComplete="off" />
</div>
```

### عدم ذخیره اطلاعات کارت

اسکیمای دیتابیس **هیچ فیلدی** برای شماره کارت، CVV2، تاریخ انقضا یا رمز دوم
ندارد. جدول `Payment` فقط این‌ها را نگه می‌دارد:

- `authority` — شناسه تراکنش درگاه
- `referenceId` — شماره پیگیری پس از موفقیت
- `cardPanMasked` — **چهار رقم آخر** برای نمایش به مشتری
- `gatewayPayload` — پاسخ خام درگاه برای پیگیری اختلاف

مالکیت کارت توسط درگاه دارای مجوز شاپرک انجام می‌شود، نه نودهی.

## ۲. آنچه پیش از انتشار باید تکمیل شود

### احراز هویت و کنترل دسترسی

ورود فقط با **شماره همراه + کد یک‌بارمصرف** است؛ رمز عبوری وجود ندارد، پس چیزی
برای لو رفتن یا به‌خاطر سپردن وجود ندارد. پیاده‌سازی: `src/lib/server/auth/`.

پیاده‌شده و آزموده‌شده:

- [x] کد یک‌بارمصرف ۵ رقمی، ذخیره‌شده به‌صورت **هش** (SHA-256 با شماره به‌عنوان نمک)؛ کد خام هرگز ذخیره نمی‌شود
- [x] عمر کد ۲ دقیقه، حداکثر ۵ تلاش، ابطال کد قبلی با هر ارسال تازه، مصرف یک‌باره
- [x] محدودیت نرخ بر اساس **هم شماره و هم IP** (۳ در ۲ دقیقه برای شماره، ۱۰ در ساعت برای IP)
- [x] مقایسه هش کد با `timingSafeEqual` — بدون افشای زمان مقایسه
- [x] توکن نشست فقط در کوکی `httpOnly` می‌رود؛ در دیتابیس فقط **هش** آن است
- [x] کوکی با `sameSite=lax` و در تولید `secure`
- [x] کنترل دسترسی نقش‌محور سمت **سرور** (`getStaffUser`) — نه پنهان‌کردن دکمه در مرورگر
- [x] کاربر بدون نقش مدیریتی در `/admin` صفحه ۴۰۴ می‌بیند، نه پیام «دسترسی ندارید»
- [x] بررسی مالکیت در سطح رکورد برای سفارش‌ها یک کاربر و آدرس‌های او
- [x] خروج، رکورد نشست را از دیتابیس حذف می‌کند (کوکی دزدیده‌شده بی‌اعتبار می‌شود)
- [x] هر عمل مدیریتی در `AuditLog` با شناسه کاربر، IP و زمان ثبت می‌شود

باقی‌مانده پیش از انتشار:

- [ ] **ارتقای هش کد به Argon2id.** فضای کد ۵ رقمی فقط ۱۰۰٫۰۰۰ حالت دارد و
  SHA-256 برای حمله آفلاین روی نسخه پشتیبان لو‌رفته بسیار سریع است. خطر عملی
  کم است (کد ۲ دقیقه عمر دارد، یک‌بار مصرف است و سقف تلاش دارد)، اما پس از لو
  رفتن دیتابیس، هش ارزان ارزش حدس زدن را دارد. ارتقا فقط تغییر `hashOtp` است.
- [ ] احراز هویت دو مرحله‌ای **اجباری** برای نقش‌های `admin`، `accountant`، `operator`
- [ ] قفل موقت شماره پس از ۵ تلاش ناموفق (`lockedUntil`) — الان محدودیت نرخ و
  سقف تلاش جلوی حمله را می‌گیرد ولی شماره قفل نمی‌شود
- [ ] امکان «خروج از همه دستگاه‌ها» (حذف تمام رکوردهای `Session` یک کاربر)
  — ساختار جدول آماده است، فقط کنش آن در رابط کاربری نیست
- [ ] بازبینی دوره‌ای سطح دسترسی نقش‌ها و نشست‌های فعال

### کنترل دسترسی در سطح رکورد

این مهم‌ترین آسیب‌پذیری رایج در فروشگاه‌هاست. **بررسی هویت کافی نیست؛ باید
مالکیت بررسی شود.**

```ts
// ❌ آسیب‌پذیر — هر کاربر واردشده‌ای می‌تواند سفارش دیگران را ببیند
const order = await prisma.order.findUnique({ where: { orderNumber } })

// ✅ درست — مالکیت بررسی می‌شود
const order = await prisma.order.findFirst({
  where: { orderNumber, userId: session.user.id },
})
if (!order) return new Response('یافت نشد', { status: 404 })
```

همین قاعده برای `Address`، `Review`، `WishlistItem`، `CartItem` و `Invoice`
لازم است. برای پیگیری سفارش مهمان، علاوه بر شماره سفارش، **شماره همراه ثبت‌شده**
را هم بخواهید و تطبیق دهید — در `/api/orders/track` همین کار انجام می‌شود و
شماره سفارش درست با شماره همراه نادرست، **همان** پاسخ ۴۰۴ می‌گیرد تا کسی با
تفاوت پاسخ‌ها وجود یک سفارش را کشف نکند.

وضعیت کنونی:

| منبع | نحوه محافظت | فایل |
| --- | --- | --- |
| سفارش کاربر | `findMany({ where: { userId } })` | `src/lib/server/orders.ts` |
| آدرس کاربر | `findFirst({ where: { id, userId } })` | `src/lib/server/addresses.ts` |
| نظر کاربر | `where: { userId: user.id }` | `app/account/reviews/page.tsx` |
| صف‌های مدیریتی | `getStaffUser()` پیش از هر کوئری | `src/lib/server/admin.ts` |
| پیگیری مهمان | `orderNumber` **و** `customerPhone` | `src/lib/server/orders.ts` |

### CSRF

- توکن CSRF برای تمام درخواست‌های تغییردهنده (`POST`، `PUT`، `PATCH`، `DELETE`)
- کوکی نشست با `SameSite=Lax` (و `Strict` برای مسیرهای حساس)
- بررسی هدر `Origin` در API Routes

نکته: Server Actions در Next.js محافظت داخلی دارند، اما فرض نکنید همه چیز
پوشش داده شده — API Routes را جدا محافظت کنید.

### اعتبارسنجی سرور

اعتبارسنجی کلاینت (که در فرم‌ها پیاده شده) فقط برای تجربه کاربری است و
**هرگز** جای اعتبارسنجی سرور را نمی‌گیرد. در سرور با **Zod** تکرار کنید:

```ts
const orderSchema = z.object({
  receiverName: z.string().min(3).max(100),
  receiverPhone: z.string().regex(/^09\d{9}$/),
  postalCode: z.string().regex(/^\d{10}$/),
  addressLine: z.string().min(10).max(500),
  items: z.array(z.object({ productId: z.string().cuid(), quantity: z.number().int().min(1).max(20) })).min(1),
})
```

اعتبارسنجی حیاتی پرداخت: **مبلغ باید در سرور و از دیتابیس محاسبه شود.** اگر
مبلغی از کلاینت می‌آید و در سرور بازمحاسبه نمی‌شود، کاربر می‌تواند قیمت یک
یخچال را به هزار تومان تغییر دهد.

### امنیت وب‌هوک

- [ ] بررسی امضای HMAC-SHA256 با `timingSafeEqual`
- [ ] رد درخواست با timestamp قدیمی‌تر از ۵ دقیقه (جلوگیری از بازپخش)
- [ ] جلوگیری از پردازش تکراری با `deliveryId`
- [ ] محدودیت حجم بدنه درخواست
- [ ] لاگ تمام وب‌هوک‌های ورودی در جدول `WebhookLog`

### لاگ حسابرسی

اتوماسیون `AuditLog` برای این کنش‌ها الزامی است:

- ورود و خروج مدیران (موفق و ناموفق)
- تغییر وضعیت سفارش
- تغییر قیمت محصول
- حذف یا بایگانی محصول
- تغییر موجودی به‌صورت دستی
- تغییر سطح دسترسی کاربران
- صدور و ابطال کد تخفیف
- مشاهده اطلاعات مشتریان توسط کارکنان

هر رکورد شامل: کاربر، کنش، موجودیت، مقدار قبل و بعد، IP و user agent. لاگ
**فقط افزودنی** باشد؛ هیچ نقشی نباید امکان ویرایش یا حذف لاگ را داشته باشد.

## ۳. مدل تهدید — سناریوهای واقعی

| تهدید | پیامد | کنترل |
| --- | --- | --- |
| دستکاری قیمت در کلاینت | فروش کالا به قیمت ناچیز | محاسبه مجدد مبلغ در سرور از دیتابیس |
| جعل بازگشت از درگاه | سفارش پرداخت‌شده بدون واریز واقعی | استعلام از API درگاه، عدم اعتماد به query string |
| مشاهده سفارش دیگران | نشت اطلاعات شخصی | بررسی مالکیت در سطح رکورد |
| اسکریپت روی صفحات | دزدیدن نشست کاربران | CSP، escape خروجی، عدم اجرای HTML ورودی |
| درخواست ساختگی وب‌هوک | تغییر موجودی و ثبت سفارش جعلی | امضای HMAC + بررسی timestamp + idempotency |
| حملات Brute Force روی OTP | هزینه پیامک و دسترسی به حساب | محدودیت نرخ روی شماره و IP، قفل موقت |
| تزریق SQL | نشت کل دیتابیس | استفاده از Prisma، پرهیز از کوئری خام |
| سوءاستفاده از کد تخفیف | زیان مالی | محدودیت استفاده کل و به‌ازای هر کاربر، بررسی در تراکنش |
| خودرنسانی موجودی با درخواست هم‌زمان | فروش کالای ناموجود | تراکنش دیتابیس + قفل روی رکورد موجودی |

### نکته درباره رقابت در موجودی

اگر دو کاربر هم‌زمان آخرین کالا را خرید کنند، بدون قفل مناسب هر دو سفارش ثبت
می‌شود و یکی از آن‌ها کالا نمی‌گیرد. راه‌حل: کاهش شرطی موجودی در یک تراکنش:

```ts
const updated = await prisma.product.updateMany({
  where: { id: productId, stock: { gte: quantity } }, // شرط در WHERE
  data: { stock: { decrement: quantity } },
})
if (updated.count === 0) throw new Error('موجودی کافی نیست')
```

نکته کلیدی: شرط موجودی باید **داخل `WHERE`** باشد، نه اینکه ابتدا بخوانید و
بعد بررسی کنید. در حالت دوم، بین خواندن و نوشتن پنجره رقابتی وجود دارد.

## گزارش آسیب‌پذیری

اگر آسیب‌پذیری امنیتی پیدا کردید، لطفاً آن را در مخزن عمومی منتشر نکنید.
مستقیم به `security@nodehi.ir` گزارش دهید. تلاش می‌کنیم حداکثر تا ۷۲ ساعت
پاسخ اولیه بدهیم و پس از رفع، از شما به‌عنوان گزارش‌دهنده تقدیر کنیم.
